ARCHITECTURAL RULE
Nothing becomes advisor-visible merely because it exists inside VYNE OS. Every advisor-facing item must be intentionally published, versioned and permissioned.
1. Experience Promise
The advisor should experience VYNE as calm, private, intelligent and unusually clear. The process should reduce noise without concealing trade-offs.
DESIRED REACTION
I finally understand the decision, what matters most, what remains unknown and what I should do next.
The experience must never feel like:
A recruiting funnel disguised as advice
A software demo that places the advisor inside VYNE's internal workflow
A data-entry exercise
A high-pressure comparison of firms before objectives are clear
A black-box model that produces an unexplained answer
A portal filled with documents the advisor cannot interpret
2. The Experience Principles
Principle

4. Advisor State
Advisor State is a required operating consideration, not a personality label. It captures the advisor's readiness, confidence, trust and cognitive load at a specific point in the decision.
State dimension
Examples
Consultant response
Trust
Guarded, testing, open, dependent
Earn permission; never exploit reliance.
Clarity
Confused, exploring, focused, decided
Match the amount of information to the advisor's ability to use it.
Readiness
Curious, preparing, active, committed
Do not advance the process faster than readiness supports.
Emotional load
Calm, frustrated, fearful, exhausted, energized
Acknowledge the condition without allowing emotion to silently govern the decision.
Team alignment
Unknown, divided, cautiously aligned, committed
Treat each material stakeholder as a separate source of readiness.
Evidence confidence
Low, mixed, sufficient, verified
Direct work toward decision-changing unknowns.
USE RULE
Advisor State informs how the meeting is run. It does not become a score used to manipulate the advisor.

17. Security and Privacy Boundaries
Separating VYNE OS and Advisor Studio reduces risk only if the separation is enforced technically and operationally.
Use distinct roles and permissions for founder, consultant, recruiter, operations and advisor.
An advisor may access only the advisor's own workspace and explicitly shared team materials.
Internal notes, fee data and unrelated advisor records must be inaccessible at the application and database layers.
Uploads require malware scanning, encryption, access logging and retention rules in a production system.
Authentication, password recovery, session management and multifactor authentication must be production-grade before confidential use.
The current single-file prototype may support design and demonstration but should not hold production advisor data.
Exports saved to VYNE OS must retain version, source and publication status.

19. Presentation Mode
Presentation Mode should be preserved and redesigned as an advisor conversation surface.
Hide internal navigation, edit controls and confidential fields.
Show the decision question, assumptions, scenarios and trade-offs in a clear sequence.
Allow the consultant to reveal detail progressively rather than exposing a dense model all at once.
Display a visible version date and data-as-of date.
Provide an advisor-safe print or PDF output.
Never make a scenario appear recommended merely because it is visually highlighted.

22. Immediate Product Decision
RECOMMENDED PATH
Keep the model and deal builder as a separate Advisor Modeling Workspace for now. Use Presentation Mode and PDF exports with advisors. Save approved snapshots and notes back to the founder CRM. Build the full Advisor Studio only after the workflow and security requirements are proven.
This approach is faster, safer and less expensive than attempting to turn the current CRM prototype into a multi-user advisor portal immediately. It preserves the strongest parts of the existing work while preventing internal and advisor-facing requirements from becoming entangled.
